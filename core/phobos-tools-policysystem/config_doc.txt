
1. What enforces a [connect] rule

The allow-list is the [connect] section of a policy cfg (see the README's
configuration format), turned into two kernel- and syscall-level expressions of
the same rules, with an optional third for host names:

- Concrete TCP ports are handed to Landlock as `--connect-tcp`. This is the
  kernel-enforced half: a connect to a port no rule names is refused by Landlock
  itself, and it cannot be stepped around from inside the process.
- The host/address rules are read by the connect guard (phobos-seccomp-networksystem),
  which supervises every connect() with a seccomp user-notification and makes an
  allowed connection itself. Where it runs it is the whole connect boundary, host
  and port, from outside the process, which a raw system call cannot step around.
  It holds an IP-literal rule to that exact address, the name localhost to the
  loopback range (every 127.x.x.x address and ::1), an IP-range rule (addr/prefix)
  to that network, and a rule that names a DNS
  hostname it cannot tie to an address to its port alone.
- A rule that names a DNS hostname is enforced by host by the egress broker,
  which the network layer starts automatically whenever a [connect] rule names a
  host: the broker (an HAProxy the network layer starts) reads the TLS host name
  from the ClientHello, which the guard cannot see, and for an exact name resolves
  it itself and connects only to that address. The network layer refuses an
  exact-name rule when no resolver is given, rather than run with a name the
  broker cannot pin to an address.
- A host name with a star in it, such as `*.example.org`, is refused (PHB-EPOLICY)
  for either transport, because a wildcard cannot be resolved to an address and
  would constrain nothing about where the connection goes. Name each host exactly.
  The bare `*`, which names every host, is the one star that stays. The parser, the
  merged-policy check, the network layer and the broker's config generator each
  refuse it, so a specification written by hand is judged too, and the connect
  guard drops such a row itself, which denies, rather than read it as an unknown
  name that matches every address on its port.

A [connect] rule may end with a transport marker, `udp` or `tcp`. The marker is
optional and defaults to tcp, so every existing rule keeps its meaning. A `udp`
rule is handed to Landlock as `--connect-udp` (the CONNECT_SEND_UDP right, which
covers both connecting a datagram socket and sending a datagram to a remote port),
and the connect guard enforces it for the UDP transport apart from TCP, so a udp
rule never admits a TCP connection to the same host and port, nor the reverse. UDP
needs Landlock version 10; on an older kernel a udp rule is refused (PHB-EPOLICY)
rather than run with UDP left unenforced. There is no egress broker for UDP, whose
host enforcement rests on the TLS host name, so a udp [connect] rule that names a
DNS host is held to the addresses the name had when the run began: the network layer
asks the resolver given with --resolver once, before the command starts, hands the
connect guard one rule for each address (at most sixteen) and maps the name to those
addresses in /etc/hosts for the command. A name that does not resolve refuses the run
(PHB-ERUNTIME), as does a missing --resolver, an /etc/hosts that already maps the name to a different set of addresses, more than 64 names, and names and ports whose addresses add up to more
than the 256 rules the guard keeps. An address the name gains later is not followed, and
an answer is only read for the name asked and the aliases that lead from it. A name with a
star in it is refused as for tcp.

There is no `openConnections` / `sendData` / `receiveData` toggle: a rule names a
host, a port and a transport, or it does not.


2. What enforces a [bind] rule

The [bind] section names local TCP ports a submission may listen on, one bare
port per line. Bind is closed unless a [bind] row opens it: the network layer
always applies a network-only Landlock ruleset with `--close-bind`, so a run with
no [bind] rule, or given no --config, binds nothing. Each port becomes a Landlock
`--bind-tcp` rule. Port 0 becomes `--ephemeral-bind-tcp` instead, which grants only
a port the kernel chooses and never a port the submission names; the shipped Java
policy carries it for Gradle. Because a socket that was never bound gets such a
port when it listens, a port 0 row is also what lets the connect guard allow that
listen (`--allow-ephemeral-listen`). Landlock's bind right is per-port and cannot
narrow to a local address, so a [bind] rule may name only a port and one that
names an address is refused (PHB-EPOLICY). A listener's reachability from outside is
governed by the [accept] section (an inbound HAProxy that filters by source
address) and the container's network isolation, not by the bind address.

A [bind] rule may likewise end with `udp`, handed to Landlock as `--bind-udp`; the
marker defaults to tcp. When a run handles both a udp bind and a udp connect rule,
Phobos also grants `--bind-udp` on port 0 (any local port), because the kernel
auto-binds an ephemeral UDP source port for an outgoing datagram and gates that
auto-bind by BIND_UDP, which is now always handled, so any udp [connect] rule
brings the port 0 grant with it. UDP bind needs Landlock version 10. The connect
guard runs outside Landlock and makes every datagram connect and send itself, so
it judges that source port too: a connect or send on a socket that was never bound
is refused unless the policy has such a row or any udp [connect] rule, which the
network layer tells it with --allow-ephemeral-udp-bind.

On a kernel below Landlock version 4 (TCP) or 10 (UDP) the bind cannot be closed.
The enforcer says so on every run and leaves the bind open, and
--minimum-landlock-version in the tail flags makes it a refusal. An explicit port
rule, unlike the port 0 grant, still refuses a kernel that cannot handle it.


3. What is not filtered in-process

Phobos filters outbound stream connect() from outside the process, at the seccomp
and Landlock boundaries, and does not interpose any libc call inside the process.
On a Landlock version 10 kernel it also enforces UDP ports (connect/send and bind)
at those boundaries when the policy names them; on an older kernel a udp rule is
refused rather than left unenforced. Host-level UDP egress beyond the allow-list
and inbound connections a [accept] rule does not front are governed by the
container the run is placed in
(`--network none`, or the operator's firewall in a networked posture), as
SECURITY.md states.
